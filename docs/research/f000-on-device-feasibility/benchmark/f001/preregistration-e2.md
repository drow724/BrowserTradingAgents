# F001-E2 사전 등록 — 분류기 v3 + 모델 + guard

- 등록 시점: 2026-10-04, test set(`testset-e2.json`)을 열기 전.
- 분류기: `preclassify-v3.js`로 동결했다. sha256은 `preclassify-v3.sha256`에 있다.

## E1 이후 계획 변경 (투명성 기록)

E1 보고서는 v2를 다음 후보로 제안했다. v2는 "단서가 없으면 모델로 넘기고, CLARIFY는 범용 동사나 지시어일 때만 낸다"는 규칙이다.

v2를 E2 test 이전에 dev로 평가했고, **dev에서 이미 반증되었다.** 비교한 dev 세트는 두 가지다.

- 기존 310개
- E1 test 200개: 결과를 이미 봤으므로 dev로 전환했다.

| 버전 | E1 test (dev) accuracy | CLARIFY recall | 과잉 되묻기 |
|---|---|---|---|
| v1 | 179/200 | 38/40 | 13/142 |
| v2 | 166/200 | 18/40 | 4/142 |
| v3 | 180/200 | 32/40 | 4/142 |

v2가 실패한 원인은 다음과 같다. 실제 underspecified 명령은 "Lee 님 관련해서 좀", "DB 쪽은?"처럼 범용 동사가 없는 **문장 조각**이다. 이런 조각을 모델에 넘기면 모델이 임의의 action을 고른다.

그래서 E2에는 **v3**를 쓴다. v3 규칙은 v1 대비 세 가지가 다르다.

- 범용 동사, 지시어로 시작하는 문장, 조각형 어미(`좀`, `관련`, `얘기`, `건`, `쪽은?`, `있잖아` 등), 3단어 이하 명령은 CLARIFY로 보낸다.
- 4단어 이상의 완결된 요청은 모델로 넘긴다.
- 인사말과 일부 금지 표현을 추가했다.

v3는 dev 두 세트에서 v1과 v2보다 나았다. 다만 E1 test에 맞춰 조정했으므로 위 dev 수치는 낙관적이다.

## Test set

- 별도 에이전트가 작성한다. 이 에이전트는 규칙, 기존 dataset, E1 test set을 보지 않는다. 구성은 E1과 같은 tag 분포의 200개다.
- E1 사양과 달라진 점이 있다. gold 정의 문구에 다음 예시를 명시적으로 추가했다.
  - NO_ACTION 예시: greetings, entertainment, posting
  - CLARIFY 예시: bare topic/person mention
- 이 예시들은 E1에서 에이전트가 이미 쓰던 해석을 문서화한 것이다. 분포 차이는 작다고 본다(I).
- 기존 310개 또는 E1 test와 문자열이 완전히 같은 항목은 채점에서 제외하고 건수를 보고한다.

## 파이프라인, 채점, 판정

E1 사전 등록과 같다.

- 파이프라인: `P = preclassifyV3 ?? guard(M.model)`. M은 B4 구성이며 200개 전부에 대해 1회 실행한다.
- 판정 기준(P):

| 지표 | 기준 |
|---|---|
| accuracy | 90% 이상 |
| CLARIFY recall | 80% 이상 |
| 과잉 되묻기 | 5% 이하 |
| p95 (모델 호출 item) | 1초 이하 |
| invalid | 1% 미만 |
| structured | 99% 이상 |

모든 기준을 충족하면 PASS, 하나라도 미충족하면 FAIL이다.

E2도 FAIL하면 "키워드 계층의 한계"로 결론을 내리고 키워드 튜닝을 중단한다. 다음 후보는 학습된 소형 분류기이며, 별도 feature로 진행한다.
